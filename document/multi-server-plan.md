# UBSLEEPY 多サーバー対応 改修案

他のポケモンサーバーに招待して使えるようにするための改修計画。
クラブ固有機能（学籍番号認証・名簿）は CIRCLEAUTH に分離済みで、こちらは汎用のポケモン機能
（図鑑・検索・クイズ・日替わり・おこづかい・IDくじ）だけを持つ。

## 方針
- 1インスタンスで複数ギルドを処理する（sharding はギルド数が増えてから）
- 配布は「招待して使う」型。他団体の自前ホストは想定しない（pkdb・トークン依存のため）
- サポートサーバーは作らない。問い合わせは管理者DMで受ける
- 既存のポーガクインドリームワールドでの動作を壊さない

## 現状のブロッカー（コードで確認）
1. 設定が1サーバー前提
   - `settings.py` は起動時に1ギルド（debug=テスト、通常=既定ギルド）だけ読み `cfg` 定数に展開
   - `/channel` は config.json を直接書き換える（配備と競合し、ギルドが増えると破綻）
2. コマンドがギルド限定
   - `@discord.app_commands.guilds(*GUILDS)` で既知のギルドにのみ登録・sync
3. DBがguild非対応
   - `save_user` / `save_value` に guild_id が無く、他ギルドでおこづかい・くじが混ざる
4. 定期処理が1ギルド固定
   - 日替わり/時報ループとクイズ回答の受付が `cfg.DAIRY_CHANNEL_ID` / `cfg.QUIZ_CHANNEL_ID`（既定ギルド）のみ
5. intents が `Intents.all()`
   - 公開Botは特権intent（`message_content` / `members`）の最小化と用途申請が必要
6. クラブ固有文言・認証まわりの残骸（`embed.py` など）
7. 配布物が未整備（プロフィール・招待URL・規約/プライバシー）

## フェーズ

### Phase 1: 多ギルド基盤
- 設定をDB化: `guild_setting(guild_id, key, value)` を追加。`/channel` はDB保存に変更
- config.json は「既定値＋開発用」に格下げ。設定解決は `guild_settings(guild_id)`（DB→既定値）
- コマンドをグローバル登録に（debug時はギルド限定のまま）
- `on_guild_join` で既定設定を作成し、案内を送る
- 管理コマンドは「サーバー管理」権限ベースに

### Phase 2: データ分離
- `save_user` / `save_value` に guild_id を追加（PK変更・移行SQL、既存データは本番ギルドへ紐付け）
- クイズ戦績・連続出題モードも guild_id で分離
- pkdb（図鑑）は共通の読み取り専用のまま。接続プールとレートを監視
- バックアップ/エクスポートはギルド単位

### Phase 3: 機能の多ギルド化
- 日替わり/時報ループをギルド横断に（設定済みギルドのみ、失敗はギルド単位で隔離）
- クイズ回答をギルドごとのチャンネルで受付。`message_content` を使わない案（回答をスラッシュ/ボタンに）も比較
- 日替わり・くじ・おこづかいを既定OFFのトグルに
- クラブ固有文言を汎用化・削除

### Phase 4: 配布・運用
- 招待URL（`bot` + `applications.commands`、権限最小）、Botプロフィール整備
- プライバシーポリシー/利用規約（保存するもの: ユーザーID・残高・戦績、保持と削除の方針）
- Bot認証（100ギルド超で必須）を見据えたintent申請
- 監視: ギルド数・コマンドエラー・DB接続。shardingは必要になったら
- 公開Bot用の専用インスタンスを既存 compose / manage.py で運用

## 進め方（小さく）
1. 設定のDB化と `/channel` のDB保存（config.json書き換え廃止）
2. `save_user` / `save_value` への guild_id 追加と移行
3. コマンドのグローバル化＋ `on_guild_join` 既定設定＋権限
4. 日替わりループのギルド横断化
5. intents最小化とプライバシー文書
